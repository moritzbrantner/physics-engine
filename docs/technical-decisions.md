# Technical decisions

Record consequential engineering choices here only when existing domain-specific documents
do not already explain them. [AGENTS.md](../AGENTS.md) owns general implementation boundaries;
[numerics.md](numerics.md) owns precision rules; [world-api-contract.md](world-api-contract.md)
owns which world APIs and capabilities consumers can rely on. Source code and tests,
not this register, prove what is implemented. GitHub issues track remaining work.

## Independent physics reference

### TECH-001 — Use Rapier as a reference, not an automatic solver replacement

- **Basis / status:** Existing selected technical direction in
  [physics-engine #279](https://github.com/moritzbrantner/physics-engine/issues/279),
  following [reuse-first ADR 0001](https://github.com/moritzbrantner/coding-agent-conventions/blob/main/docs/adr/0001-capability-internalization.md)
  and the [consumer-driven roadmap #191](https://github.com/moritzbrantner/physics-engine/issues/191).
  This record does **not** approve a game default switch.
- **Selected approach:** Keep **physics-engine** authoritative for its own world, contact,
  CCD, response, wake/sleep and recovery semantics, using domain-neutral
  **rust-kernels** geometry. Compare the evolving persistent **approximate::World**
  against pinned, independent Rapier scenarios. Preserve the supported **World**
  and **RotatingWorld3d** surfaces while their consumers rely on them.
  Rapier may remain authoritative in a consumer with an explicit local decision
  (for example [worldgen](https://github.com/moritzbrantner/worldgen/blob/main/AGENTS.md));
  that does not change this repository's simulation authority.
- **Why:** A maintained external engine supplies independent physical reference
  behavior and a complete-call performance baseline. It does not define this engine's
  numerical tolerances, checkpoint format, event ordering or game-specific rules.
  Share fixture inputs and observation categories; do not attempt byte-identical
  trajectories or hide meaningful divergent physical outcomes.
- **Alternatives:** Promoting Rapier directly in all consumers would bypass their
  migration/recovery acceptance. Internal-only comparison would lack a mature
  independent solver. A universal provider interface or shadow physics in game
  production paths is unjustified until a real consumer needs it. Prefer scoped,
  diagnostic adapters to the existing public world APIs.
- **Evidence today:** [Collision Lab](https://github.com/moritzbrantner/collision-lab/blob/main/Cargo.toml)
  pins Rapier 0.36.0 and already has
  [Rapier benchmark fixtures](https://github.com/moritzbrantner/collision-lab/blob/main/benches/rapier_scenarios.rs).
  Those fixtures use **sensor collider intersections/pair-set parity**, not
  Rapier's persistent rigid-body contact/impulse solver; they do not prove
  dynamic stack, friction, CCD, sleep or checkpoint parity.
  Our own [f32 precision tests](../tests/f32_precision_envelope.rs) exercise the
  documented envelope, not a Rapier comparison. No comparative full-solver
  result or consumer cutover is claimed.
- **Verification before promotion:** Extend existing reference fixtures to
  complete, equal-input persistent stepping; check independent invariants for
  static/dynamic contact, capsule grounding, supported friction, fast CCD,
  finite state, sleep/wake, failure/recovery and representative crowded workloads.
  Report exact library/repository revisions, build scalar (the f32-physics game
  target and f64 reference where useful), timestep, tolerated differences and
  unsupported capabilities. Compare whole-step latency, worst stalls, work,
  memory and lifecycle costs without reusing a sensor-only time as solver time.
  Keep existing native/WASM replay and physical-quality checks. Run real consumer
  acceptance under [MMORPG #165](https://github.com/moritzbrantner/mmorpg/issues/165)
  and [ARPG #162](https://github.com/moritzbrantner/arpg/issues/162); actual
  migration remains with their owning issues and separate owner approval.
- **Revisit when:** Comparable persistent-solver evidence changes the trade-off,
  a named consumer proves a different provider meets its exact gameplay and
  recovery contract, or the reference dependency's supported behavior changes.
  Do not silently change game defaults, checkpoints or physics ownership.

## External-first adoption for new consumers

### TECH-002 — Prefer an established external physics provider when a new consumer needs unsupported first-party capabilities

- **Approval / basis:** Owner-selected on 2026-10-15 in physics-engine /tech-steer Question 1, option B (external-first). This extends [TECH-001](#tech-001--use-rapier-as-a-reference-not-an-automatic-solver-replacement) and follows [reuse-first ADR 0001](https://github.com/moritzbrantner/coding-agent-conventions/blob/main/docs/adr/0001-capability-internalization.md).
- **Context:** A new game may require dependable character collision, joints, or another feature before the first-party engine provides it within that consumer's correctness, recovery and runtime requirements.
- **Selected approach:** Use a suitable maintained external implementation such as Rapier for the missing capability in a **new consumer**, rather than delay its user-visible functionality for first-party parity. Make the chosen provider and its physical authority explicit in the consuming repository. Keep developing and independently validating the first-party physics engine as a replacement candidate; consumer adoption happens only after its actual needed features and recovery/performance contract have been proven and the owning consumer approves the switch.
- **Authority boundaries:** This policy does not migrate or change existing MMORPG, ARPG, Battle Royale or other current production backends. Do not silently run two authoritative solvers for the same interacting physics state, copy consumer gameplay logic into the engine, or invent a universal provider interface before a real need. Provider selection and save/recovery compatibility are consumer-owned contracts; physics-engine owns only its own world, collision and checkpoint semantics.
- **Alternatives considered:** First-party-only would block game delivery on an incomplete foundation. Dual production providers in every new game would impose integration and maintenance overhead without evidence of a need. External-first preserves game delivery while leaving future first-party adoption an evidence-based decision.
- **Evidence and handoff:** The current [world API contract](world-api-contract.md) identifies unsupported capabilities. Existing [Rapier reference work #279](https://github.com/moritzbrantner/physics-engine/issues/279) can compare behavior but does not establish universal interchangeability. [Worldgen](https://github.com/moritzbrantner/worldgen/blob/main/AGENTS.md) already keeps Rapier authoritative and the first-party solver non-authoritative. Existing-provider comparisons and migration gates remain owned by [MMORPG #165](https://github.com/moritzbrantner/mmorpg/issues/165), [MMORPG #46](https://github.com/moritzbrantner/mmorpg/issues/46), [ARPG #162](https://github.com/moritzbrantner/arpg/issues/162) and [ARPG #48](https://github.com/moritzbrantner/arpg/issues/48). Before an external selection, verify supported APIs, license, pinned version, platform behavior, performance and persistence needs in that consumer.
- **Revisit when:** A named consumer's first-party path proves its required behavior and recovery, or changing external-provider costs/requirements justify a new choice. Do not call the candidate interchangeable or migrate stored physics state without evidence.

## Cross-provider persistent-world migration

### TECH-003 — Versioned physics-provider conversion at a controlled restart

- **Approval:** Owner-selected 2026-10-15, physics-engine /tech-steer Question 2, option B: versioned migration at a controlled save/restart boundary. Extends [TECH-002](#tech-002--prefer-an-established-external-physics-provider-when-a-new-consumer-needs-unsupported-first-party-capabilities).
- **Context:** A game world saved under a mature external physics solver such as Rapier may later move to the first-party engine. A physical checkpoint preserves continuation only within its own compatible solver/build/target contract; it is not interchangeable with Rapier's internal contacts, caches, solver history, or event stream.
- **Selected approach:** At a deterministic completed-tick save/restart boundary, stop the old authoritative solver and convert **consumer-owned, versioned game/domain state** into a new first-party world. Validate persistent identity, gameplay state, authoritative positions/orientations, velocities, collider/material/unit mapping, sequencing and required inputs; then initialize fresh first-party physical contacts, warm-start, sleep/wake and derived acceleration under the replacement's documented behavior. Never deserialize Rapier checkpoint bytes into `physics-engine::approximate::Checkpoint`. Gameplay must explicitly accept potential differences in post-migration trajectories rather than claiming bit-identical replay across solvers.
- **State and authority:** The consuming application owns conversion, persistence/journal schemas, provider selection, publication and version compatibility. Physics-engine owns first-party physical validation, steps and its checkpoint API. Keep the original save and provider identity recoverable through the uncommitted conversion; publish a new provider/schema checkpoint and migration marker together only after validation. A failed conversion must not partially publish gameplay state, consume commands twice or duplicate durable rewards. Do not hot-switch solvers mid-step, run two interacting production authorities, or introduce a general provider framework without a real need.
- **Alternatives:** Permanently retain Rapier for already-created worlds (Question 2 option A) avoids conversion but prolongs maintenance and compatibility support. Translating raw provider-internal checkpoint bytes would falsely promise incompatible solver-history semantics.
- **Verification:** Each proposed consumer migration must prove a real restart with versioned fixtures, active/resting contacts, moving supports, lifecycle/IDs, valid and corrupted saves, accepted physical divergence, full gameplay/reconnect/protocol semantics, rollback on a failed conversion, idempotent journals and durable economic grants. Compare complete workloads and memory, not only a new world instantiation. Same-solver continuation remains separately exact within its documented build/target. [Physics #198](https://github.com/moritzbrantner/physics-engine/issues/198) owns first-party checkpoints; [MMORPG #46](https://github.com/moritzbrantner/mmorpg/issues/46) and [MMORPG #40](https://github.com/moritzbrantner/mmorpg/issues/40) own multiplayer migration, persistence, durability and recovery. This record does not itself approve or execute a production migration.
- **Revisit when:** A real consumer requires a materially different migration window, or tested cross-solver interchange becomes feasible. Post-cutover rollback/roll-forward remains an explicit consumer deployment choice, not an assumed engine guarantee.

## Checkpoint portability between native and browser

### TECH-004 — Keep physical checkpoints build- and target-specific

- **Approval:** Owner-selected 2026-10-15, physics-engine /tech-steer Question 3, option A. Extends [TECH-003](#tech-003--versioned-physics-provider-conversion-at-a-controlled-restart), without changing the existing physical checkpoint format or implementation.
- **Context:** The first-party [physical checkpoint contract](floating-checkpoints.md) guarantees exact continuation only for a compatible solver build and target. Native Rust and browser WASM can differ in floating-point execution, feature flags, ABI and runtime behavior; a shared byte representation alone would not prove replay portability.
- **Selected approach:** Preserve **build/target-specific** physical checkpoints. A checkpoint is restored only on its declared compatible solver/build/target, scalar width, schema, algorithm and content context, using the existing fail-closed validation. Native and WASM checkpoint continuation are independently tested; no native-to-WASM or WASM-to-native interchange is promised. When a consumer moves its authoritative simulation to another platform, it must use an explicit, versioned **consumer-owned game/domain state** conversion at a completed-tick restart boundary to reconstruct a new world, as under TECH-003, followed by a fresh compatible physical checkpoint.
- **Consequences:** A reconstructed world may have different contact/warm-start/sleep state and future trajectories. The owning game must validate its persistence, input ordering, recovery and gameplay invariants with documented tolerances. It must not silently claim cross-target bit-identical replay, accept unsupported checkpoint bytes, or reinterpret a foreign checkpoint as an in-place restore. No new portable physics wire protocol, automatic cross-target conversion layer or universal runner identity requirement is authorized.
- **Alternatives considered:** Portable native/WASM physical checkpoints (Question 3, option B) would demand a stable cross-target physical-state ABI and substantial numerical/replay and compatibility verification; that cost is not justified by a demonstrated consumer requirement. Versioned game-state restart conversion already supplies the supported platform-migration path.
- **Evidence and handoff:** Retain the existing [native and WASM same-target checkpoint checks](floating-checkpoints.md#acceptance-and-reproduction) and incompatible context/scalar-width rejection. Before a specific consumer changes its execution target, it must prove save -> stop -> convert -> validate -> restart (plus failed-conversion rollback) on real representative state. [Physics-engine #198](https://github.com/moritzbrantner/physics-engine/issues/198) owns physical continuation; consumers such as [MMORPG #46](https://github.com/moritzbrantner/mmorpg/issues/46) and [MMORPG #40](https://github.com/moritzbrantner/mmorpg/issues/40) own game persistence and migration. No portable cross-target test result or consumer migration is claimed by this decision.
- **Revisit when:** A named consumer demonstrates a requirement that cannot be met with validated game-state reconstruction and supplies evidence justifying a cross-target checkpoint contract.

## Contact-correction policy evolution

### TECH-005 — One production correction policy initially; multiple validated per-world policies later

- **Approval:** Owner-selected 2026-10-15, physics-engine `/tech-steer` Question 4: **start with A, then move toward B**. This is an approved staged direction, not a claim that B is implemented or a mandate to enable it immediately.
- **Current phase — A:** Keep **one supported production contact-correction policy** for the floating solver. The existing Baumgarte-based correction remains the production default while [#158](https://github.com/moritzbrantner/physics-engine/issues/158) evaluates softened constraints/relaxation. Such experiments remain separately identified and opt-in; no benchmark result silently promotes an experimental policy. If evidence justifies changing the single default, handle it as a reviewed semantic change with physical-quality, replay and checkpoint compatibility.
- **Long-term phase — B:** Support **multiple independently validated contact-correction algorithms selectable per physics world** when real consumers justify their distinct behavior and the necessary correctness/performance/recovery contracts are established. The owner has selected this eventual direction, but not a promotion date, an algorithm shortlist, or any live mid-step/mid-world policy-switching contract. Reuse the existing engine-owned world/contact solver; do not create parallel world authorities, an unused plugin system, or mandatory support for every experimental policy.
- **Technical boundaries:** Keep collision admission, geometry, physical response ownership, stable body IDs and deterministic time completion common. Different correction algorithms may require different constraint formulation, convergence residuals and cached impulses: never silently share incompatible warm-start history, or restore a checkpoint under a different correction policy without explicit compatibility/version checks. Keep the existing [build/target-specific checkpoint policy](#tech-004--keep-physical-checkpoints-build--and-target-specific). The detailed future policy-change lifecycle remains a separate design decision.
- **Alternatives:** Permanent single-policy support would minimize ongoing maintenance but could prevent fit-for-purpose correction methods for different real games. Supporting multiple production policies immediately would multiply quality/CI/checkpoint obligations before they have consumer evidence. The staged approach preserves both near-term simplicity and the approved long-term flexibility.
- **Evidence and gate:** The current [soft-contact experiment](soft-contact-correction.md) explicitly reports mixed results and is not production-ready by declaration. Before each new supported policy, require independent [contact-quality coverage #193](https://github.com/moritzbrantner/physics-engine/issues/193) over dense/tilted stacks, friction, impacts, moving supports, sleep/wake and no-tunneling; comparable full-step work, memory and worst-stall evidence; same-policy deterministic replays; native/WASM and f32-game-build coverage where supported; an explicit per-world policy identity and validated checkpoint/recovery behavior; and acceptance in the first real consumer. Do not weaken accepted physical thresholds or create a new benchmark/CI platform.
- **Revisit when:** A proposed experimental algorithm passes the relevant contact-quality and consumer gates, or a consumer needs distinct policies. Existing [#158](https://github.com/moritzbrantner/physics-engine/issues/158) and [#193](https://github.com/moritzbrantner/physics-engine/issues/193) own the comparative evidence and correctness work; no implementation issue is implied solely by recording the staged decision.

## Contact-correction policy lifetime

### TECH-006 — Select contact-correction policy at world creation

- **Approval:** Owner-selected 2026-10-15, physics-engine `/tech-steer` Question 5, **option A** (fixed for each world). Refines the approved future multiple-policy direction in [TECH-005](#tech-005--one-production-correction-policy-initially-multiple-validated-per-world-policies-later); this is not a claim of current multi-policy production support.
- **Selected approach:** When more than one independently validated production correction policy exists, choose a **single policy as part of the world-creation configuration**. That selection remains immutable for the lifetime of the world. A change to another policy requires an explicit, controlled **stop/restart and physical-world reconstruction** at a completed simulation-tick boundary, not a live per-frame or mid-tick toggle. Consumers retain ownership of any game-state conversion and recovery boundary.
- **Why:** Different correction algorithms may use incompatible constraint rows, convergence rules, impulses and warm-start caches. A live change could silently reinterpret accumulated contact history or change simulation and replay semantics. A restart makes the physical discontinuity and compatibility contract explicit.
- **Alternatives:** In-place selection at a safe tick boundary (Question 5, option B) could support real-time algorithm tuning, but would require separate contact-cache invalidation/reinitialization, continuity semantics and replay evidence. That complexity has no validated consumer justification today.
- **Compatibility:** Record the chosen policy and any algorithm version in a future world/checkpoint compatibility identity. Do not restore a snapshot from a different correction policy into the new world unless that specific conversion is independently defined and verified. A policy switch may change future physical trajectories, support and settling; reconstruction cannot claim bit-identical continuation. Preserve [TECH-004](#tech-004--keep-physical-checkpoints-build--and-target-specific) build/target-specific checkpoint guarantees and the consumer-owned versioned migration boundary in [TECH-003](#tech-003--versioned-physics-provider-conversion-at-a-controlled-restart).
- **Evidence / activation condition:** The production default remains the existing Baumgarte-based policy. [#158](https://github.com/moritzbrantner/physics-engine/issues/158) owns experimental soft-contact comparison; [#193](https://github.com/moritzbrantner/physics-engine/issues/193) owns broad contact-quality acceptance. Add policy-selection APIs only after a second correction policy passes those gates and a named consumer requires it. Cover lifecycle, checkpoint mismatch rejection, deterministic same-policy continuation, failed reconstruction and appropriate per-policy native/WASM and `f32-physics` acceptance without weakening existing physical thresholds or adding a new test framework.
- **Revisit when:** A real consumer demonstrates a need for in-place policy switching and can justify its extra contact-history and recovery complexity. Such a revision requires a new explicit owner decision.

## Character locomotion

### TECH-007 — Kinematic character controller first; dynamic characters require separate justification

- **Approval / scope:** Owner-selected 2026-10-16, Physics Engine `/tech-steer` Question 6, **option A**. This is the architectural direction for [#194](https://github.com/moritzbrantner/physics-engine/issues/194), not a claim of a delivered controller or an automatic consumer migration.
- **Selected approach:** Deliver a reusable **kinematic character-movement path first**. A game supplies movement/jump intent and locomotion policy; physics-engine computes and validates collision-constrained movement through authoritative geometry, including bounded sweep/collide-and-slide, corner and crease handling, slope and step negotiation, ceilings, and support transitions as each slice becomes accepted. Characters are not required to obtain ordinary locomotion by applying forces to a simulated dynamic rigid body.
- **Ownership:** Physics-engine owns physical body/world state, collider and support/contact truth, casts and collision response; game consumers own player intent, movement speed and acceleration policy, abilities, knockback gameplay semantics, animation and network/session rules. Renderers/JavaScript must not implement alternative authoritative floor snapping, sliding or physical collision truth. Do not introduce two interacting physics authorities or a universal controller/provider framework.
- **Deferred, not approved:** Fully **dynamic rigid-body character locomotion** may be separately evaluated when a named consumer and independent physical-quality evidence justify it; option A does **not** commit to implementing option B later, to supporting both models immediately, or to automatic switching between them.
- **Compatibility and adoption:** Retain the existing `World` and `RotatingWorld3d` contracts. Keep `approximate::World` explicitly limited until the relevant query/controller contract, f32/native/WASM behavior and game acceptance are proven. The first real adoption target remains [ARPG #48](https://github.com/moritzbrantner/arpg/issues/48); MMORPG migration is independently gated by [MMORPG #46](https://github.com/moritzbrantner/mmorpg/issues/46) and its persistence/recovery requirements. No checkpoint/wire-format change or provider migration is authorized by this decision.
- **Evidence and handoff:** [#194](https://github.com/moritzbrantner/physics-engine/issues/194) owns reusable controller implementation and dedicated physical scenarios. Prove stable query/body ordering, touching and invalid-start behavior, narrow doorways, ramps, steps, corners, fast motion/no tunneling, moving supports and support loss, bounded work and replay in applicable f32, native and WASM configurations; then prove unchanged gameplay and whole-tick costs in the actual consumer. Use existing scenarios and checks, not a separate movement solver or benchmark framework.
- **Follow-on:** [TECH-008](#tech-008--retain-kinematic-controller-history-in-the-authoritative-physics-world) chooses persistent world-owned controller/support state; [TECH-009](#tech-009--use-bounded-engine-owned-impulses-for-kinematic-character-pushing) chooses bounded pushing of allowed movable objects. Neither choice promotes a consumer migration.

### TECH-008 — Retain kinematic controller history in the authoritative physics world

- **Approval / scope:** Owner-selected 2026-10-16, Physics Engine `/tech-steer` Question 7, **option B**. Refines [TECH-007](#tech-007--kinematic-character-controller-first-dynamic-characters-require-separate-justification), and applies to the future controller tracked by [#194](https://github.com/moritzbrantner/physics-engine/issues/194). The implementation, public API, and checkpoint integration are not yet shipped by this decision.
- **Selected approach:** A character participating in the kinematic controller retains its physical pose, **grounded/support state, stable supporting-body identity and relevant contact/support history inside the same authoritative physics world** as the collider and other physical bodies. Retain only history needed for deterministic collision/support continuation; reuse the world's authoritative contacts and body identities rather than creating mirrored geometry or a second independent contact authority. Games submit movement/jump intent and game-selected locomotion policy; the world resolves and reports supported physical outcomes.
- **Lifecycle and ordering:** Controller state is tied to the authoritative character body identity and its creation/removal, with explicit initialization and cleanup. Deterministically invalidate stale support references on support disappearance, body removal or identity reuse, and handle support change, departure, wake/sleep interaction, and moving-platform carry in the same ordered physics step. Do not scan every character or all bodies for unrelated local changes; retain/index only work justified by actual queries and contacts.
- **Atomicity, recovery and compatibility:** Controller history that affects continuation is **physical state** under the existing [failure-safe steps and checkpoint contract](floating-checkpoints.md) and [#198](https://github.com/moritzbrantner/physics-engine/issues/198): it must roll back with a failed step and be captured/restored in canonical order at a supported safe boundary, with precise validation and format/algorithm version changes when actually implemented. Retain the [TECH-004](#tech-004--keep-physical-checkpoints-build--and-target-specific) same-build/target physical checkpoint promise; native/WASM or external-provider transfers use [TECH-003](#tech-003--versioned-physics-provider-conversion-at-a-controlled-restart) consumer-owned restart reconstruction, not interchangeable checkpoint bytes. This record does **not** change the present checkpoint layout or version.
- **Authority and alternatives:** World-owned physical controller history does not transfer gameplay actions, movement tuning, input handling, entity persistence, multiplayer leases, or animation into physics-engine. Recomputing all support state from independent stateless queries each tick (option A) loses explicit physical lifecycle and continuity. Retaining separate controller instances (option C) creates synchronization and recovery boundaries across duplicated authority. Do not introduce a second world/solver, detached controller cache, universal adapter or gameplay-side floor snapping.
- **Adoption and evidence:** [#194](https://github.com/moritzbrantner/physics-engine/issues/194) owns the Rust character scenario and engine API/acceptance, including stable identifiers, support changes/removal/reuse, moving platforms, slopes/stairs/corners/ceilings, invalid initial contacts, failed ticks, same-mode checkpoint continuation and bounded local work. [ARPG #48](https://github.com/moritzbrantner/arpg/issues/48) remains the initial consumer and must show real gameplay equivalence before switching; [MMORPG #46](https://github.com/moritzbrantner/mmorpg/issues/46) separately gates persistence, one-zone authority and reconnection semantics. [TECH-009](#tech-009--use-bounded-engine-owned-impulses-for-kinematic-character-pushing) separately selects controlled physical pushing without making characters dynamically simulated bodies.

### TECH-009 — Use bounded engine-owned impulses for kinematic character pushing

- **Approval / scope:** Owner-selected 2026-10-16, Physics Engine `/tech-steer` Question 8, **option B** (bounded physical pushing). This extends [TECH-007](#tech-007--kinematic-character-controller-first-dynamic-characters-require-separate-justification) and [TECH-008](#tech-008--retain-kinematic-controller-history-in-the-authoritative-physics-world) as the future character controller's **allowed movable-body interaction** policy under [#194](https://github.com/moritzbrantner/physics-engine/issues/194). The behavior and public API are not yet implemented.
- **Selected approach:** When a kinematically moved character makes an accepted physical contact with an eligible **dynamic** object, the **same authoritative physics world** may apply a **bounded, finite, deterministic impulse** to that object through its existing rigid-body response machinery. This permits pushing crates and similar props while retaining precise intent-driven character locomotion. The push uses verified engine collision/contact witnesses; neither games nor rendering/JavaScript approximate physical impacts or modify collider poses to simulate a push.
- **Responsibility and collision constraints:** Game consumers select which character/object interactions permit pushing and their gameplay-facing movement/push policy; the engine validates and enforces effective bounds, body/motion types and collision filters. Fixed, excluded/sensor-only and independently driven bodies must not receive a character-push impulse by default. If an object cannot move sufficiently, the character's resolved travel **stops or slides** at the real obstacle; bounded pushing never authorizes tunneling, overlap, bypass of CCD, teleporting a body or secretly converting the character to a fully dynamic rigid body.
- **Authority and deterministic behavior:** The physical object remains an ordinary dynamic body in `approximate::World`, not a second game-owned solver or artificial state channel. Applied impulses, resulting contact/velocity changes and controller/support history participate in the established ordered step and failed-step rollback; duplicate retries or checkpoint continuation must not apply an accepted push twice. Preserve stable identity/tie ordering, contact admission, appropriate wake from real contact and local bounded work; do not wake uncontacted parked bodies or connect independent islands through fixed supports.
- **Alternatives and remaining design:** Option A (no pushing) would make common movable props inert; option C (fully reciprocal dynamic character locomotion) would compromise the selected kinematic character authority. [TECH-010](#tech-010--game-defined-push-strength-ceilings-with-engine-resolved-impulses) selects the push-strength limit's authority. Permission representation and automatic forced character motion from dynamic impacts remain unapproved; implementation details belong to #194 unless a consequential fork emerges.
- **Evidence / adoption gate:** Extend the existing [#194](https://github.com/moritzbrantner/physics-engine/issues/194) character scenario instead of making a separate engine. Cover pushable/light vs heavy/jammed props, permission/filter rejection, blocked passage, moving supports, slopes/corners, stable multiple-contact ordering, fast/thin obstacles, parked-body activation, body removal/ID reuse, invalid/overflow input, failed-step rollback and same-build/target capture/restore under [#198](https://github.com/moritzbrantner/physics-engine/issues/198). Prove actual bounded work and production `f32-physics` plus native/WASM acceptance where supported. [ARPG #48](https://github.com/moritzbrantner/arpg/issues/48) remains the first proposed consumer; [MMORPG #46](https://github.com/moritzbrantner/mmorpg/issues/46) retains independent game/protocol/recovery approval. No solver cutover, checkpoint version change or newly mandatory test infrastructure is approved merely by recording this decision.

### TECH-010 — Game-defined push-strength ceilings with engine-resolved impulses

- **Approval / scope:** Owner-selected 2026-10-16, Physics Engine `/tech-steer` Question 9, **option A**. Refines [TECH-009](#tech-009--use-bounded-engine-owned-impulses-for-kinematic-character-pushing); it is a policy contract for the future [character controller #194](https://github.com/moritzbrantner/physics-engine/issues/194), not an implementation or permission to migrate any game.
- **Selected approach:** The **game defines a finite, nonnegative maximum physical push impulse** appropriate to its character type, locomotion profile or ability. The engine receives the applicable policy as an explicit validated input and computes the actual physical push from admitted contact geometry and the current motion/body state, never exceeding the effective supplied ceiling. Zero means no push. Push-eligible objects still require the game-selected interaction permissions from TECH-009; a strength limit alone never grants permission to push.
- **Lifecycle and boundaries:** A game's character/ability rules determine *which* profile/limit applies; physics-engine owns validation, collision witnessing, stable contact order, impulse clamping, body response and failure behavior. Do **not** require the engine to invent a virtual character mass or derive player strength from speed alone (Question 9 option B), or require the game to issue a separate impulse command for every physical contact (option C). An ability may change its configured limit through the existing deterministic command/world update boundary, without an extra per-contact game/physics authority.
- **Collision and safety:** A limit does not guarantee the object moves. Respect actual object mass, contacts, collision filters and constraints; heavy/jammed bodies continue to block or redirect the kinematic character. Reject invalid/nonfinite inputs without saturating or silently coercing; respect TECH-009 contact-only wake admission, CCD/no-tunneling and bounded work. Do not prescribe universal game balance values, new characters, or a mandatory default push strength.
- **Replay and recovery:** A changed limit or eligibility setting that affects the next physical step is authoritative **game-supplied input/policy** and must be reproducible in the consumer's command/state history. Any retained engine controller/physical history follows [TECH-008](#tech-008--retain-kinematic-controller-history-in-the-authoritative-physics-world) and [#198](https://github.com/moritzbrantner/physics-engine/issues/198): rejected/failed steps cannot partially commit impulses or reapply them after recovery. No present physical checkpoint/schema version is changed by this document.
- **Handoff and evidence:** Keep implementation and character-prop acceptance under [physics-engine #194](https://github.com/moritzbrantner/physics-engine/issues/194); reuse existing fail-safe/contact/continuation controls in [#198](https://github.com/moritzbrantner/physics-engine/issues/198). ## Parallel execution determinism

### TECH-011 — Identical authoritative results across worker counts on the same supported build and target

- **Approval / scope:** Owner-selected 2026-10-16, Physics Engine `/tech-steer` Question 10, **option A**. Applies to future measured parallel execution under [#200](https://github.com/moritzbrantner/physics-engine/issues/200), not to present single-thread behavior or a mandate to parallelize immediately.
- **Selected guarantee:** For a **fixed supported build/target, numerical mode, initial world/checkpoint, timestep and ordered inputs**, changing the supported worker count or worker scheduling must not change observable authoritative physical state, contacts/events and their ordering, error/failure results, or same-mode checkpoint continuation. This is a worker-count-invariant replay requirement, not merely repeatability for one fixed thread configuration. Do not permit thread-count or scheduling variations to change solver convergence decisions or canonical publication ordering.
- **Execution model:** First establish measured locality and single-thread reference behavior; parallelize only work proven independent (e.g., disjoint mutable contact islands or genuinely independent query/preparation tasks). Retain one authoritative world, stable body and pair identities, canonical island/command/result ordering, and a deterministic merge/commit boundary. A single interacting physics island is never partitioned among simultaneous writers, and fixed supports cannot incorrectly join unrelated mutable islands. Avoid schedule-dependent floating-point reductions, unstable iteration or atomic races affecting results; preserve the existing bounded CCD, contact, wake, failure-rollback and full-time semantics.
- **Rollout and fallbacks:** Introduce parallel execution only when complete consumer-shaped workload evidence justifies its partitioning, synchronization and memory cost. Retain a **single-thread production fallback/reference**, including browser/WASM paths that cannot or should not use threads, and do not build a global thread pool or scheduling framework merely because parallelism is allowed. If an optimization cannot meet worker-count parity, keep it experimental or reject it rather than silently weakening the accepted guarantee.
- **Compatibility:** This decision guarantees parity **between worker counts on the same supported build/target**, not cross-compiler/CPU-feature/OS/architecture, native-to-WASM, scalar-width (`f32-physics` versus f64), solver-version or different correction-policy bit identity. Existing [TECH-004](#tech-004--keep-physical-checkpoints-build--and-target-specific) and [physical checkpoints](floating-checkpoints.md) remain build/target-specific. No new wire/checkpoint format or required worker-count compatibility field is approved by recording this decision; if implementation alters algorithm or continuation semantics, apply the existing explicit versioning contract.
- **Verification / issue handoff:** [#200](https://github.com/moritzbrantner/physics-engine/issues/200) owns measured implementation and the parallel/sequential parity gate; [#202](https://github.com/moritzbrantner/physics-engine/issues/202) owns independent deterministic reference/evidence within existing test and ratchet infrastructure. Exercise worker counts including 1 and multiple counts, different scheduling/partitioning, changing contact bridges, repeated impulses, sleep/wake, invalid inputs, returned errors and rollback, body removal/ID reuse and checkpoint continuation, using identical ordered commands. Native/WASM use only configurations actually supported. Validate physical quality and full-call work/memory; preserve unfavorable small workloads. Existing game consumers must adopt any optimized path on their own evidence, without changing one-writer zone ownership or distributing a physics step across hosts.

## Rust/WASM and JavaScript integration boundary

### TECH-012 — Embed physics in consumer Rust/WASM first; cross to JavaScript only through high-level commands and queries

- **Approval / scope:** Owner-selected 2026-10-16, Physics Engine `/tech-steer` Question 11: **start with A**, reconsider B later when justified, and require JavaScript traffic at the **highest practical command/query level** in either architecture. This refines the intended browser/native API work in [#201](https://github.com/moritzbrantner/physics-engine/issues/201) and existing Rust-owned game boundaries; it is not a claim of a new package or a changed public API.
- **Selected initial architecture (A):** A browser game compiles and links `physics-engine` as Rust code inside its **own Rust/WASM gameplay or local-simulation host**. The game owns gameplay/command semantics; the physics engine owns physical state and collision rules. Calls from the Rust gameplay code to the physics engine stay **within WASM** and need no JavaScript bridge. In hosted online play the server remains authoritative; a non-authoritative browser does not acquire physics authority by loading WASM.
- **High-level JavaScript boundary:** JavaScript issues **coarse gameplay/simulation commands**, optionally batched, and requests **coarse read-only queries** such as bounded, relevant snapshot/projection or event results. Keep complete physical stepping, contact/constraint evaluation, body-by-body mutation, broad/narrow phase, collision probes, controller behavior, and internal state iteration in Rust/WASM. Do not expose or require a JavaScript call per body, shape, contact, force, physics iteration or substep. JavaScript may present/interpolate returned state but must never recompute authoritative physics or feed render quantization back into the world.
- **Minimal crossing cost:** Design the API around a small number of semantically meaningful command/query exchanges and only the requested consumer-visible data, not entire low-level world state by default. Batch and pack outputs only when justified by real call/copy/latency evidence, with clear ordering, validation, failure, versioning and buffer-lifetime contracts. `QUERY` remains observation-only; authoritative mutations belong to commands. Avoid needless round trips, allocations, transport wrappers, or duplicate state/cache ownership across the JS/WASM boundary.
- **Later possibility (B), not an implementation commitment:** A separate reusable Physics Engine WASM package may be considered for a **named browser/JavaScript-only consumer** when it offers demonstrated value without duplicating physical authority. If built, it must also expose **coarse world-level commands and aggregated queries**, not a chatty JavaScript mirror of Rust's low-level body/solver APIs. Reuse the same physics kernels and one authoritative world; do not build a general provider/binding framework or treat both A and B as mandatory equal products today.
- **Compatibility and evidence:** Existing native Rust APIs and compatibility worlds remain unchanged; this choice does not migrate ARPG/MMORPG engines, add standalone JS bindings, alter physical checkpoints or guarantee native/WASM bit identity. Under [#201](https://github.com/moritzbrantner/physics-engine/issues/201), first inventory real browser callers and adapter calls, and validate the existing embedded Rust/WASM integration with a real end-to-end consumer (including native and browser gameplay/queries where relevant). Measure full simulation work plus JS/WASM crossings, calls, bytes copied, allocations, memory and consumer tick cost, preserving lifecycle, stable identity, errors and complete authoritative results. Consumer-owned adapters and protocols remain with the games; new standalone package work requires separate owner/consumer evidence and an explicit scoped delivery.

## Geometry-only consumers and simulator ownership

### TECH-013 — Medieval owns tactical proximity geometry without a physics-simulation dependency

- **Approval / scope:** Owner-selected 2026-10-16, revised Physics Engine `/tech-steer` Question 12, **option A**. This is a consumer ownership decision arising from [Medieval #76](https://github.com/moritzbrantner/medieval/issues/76), **not** a removal of the engine's collision/query functionality or a new physics feature.
- **Selected boundary:** Medieval currently calls `collider_contact` solely to answer an exact melee/pursuit **distance-threshold question**. Such tactical proximity, formation eligibility, movement policy and battle results belong to `medieval-core`, not a physical simulator. Replace the current sphere/point adapter with direct overflow-safe integer geometry preserving `BattlePoint`'s full coordinate range; consume existing `rust-kernels` geometry or spatial algorithms when a genuinely reusable advanced query is required. A game does not have to depend on `physics-engine` merely to calculate distances, overlaps or pathing.
- **Keep the engines' own responsibilities:** Physics Engine still owns stateful physical worlds, forces/impulses, collision response, CCD, contacts, physical constraints, wake/sleep and engine-native queries required by **actual simulation**. `rust-kernels` owns domain-neutral geometry kernels; game cores own their tactical semantics. This decision does not move engine-owned collision truth into an arbitrary game adapter, nor ban query-oriented physics APIs for genuine physics-world consumers.
- **No speculative scene product:** Do **not** build a dedicated read-only Physics Engine collision-scene API or require a complete physics world solely because Medieval performs proximity queries. The earlier `/tech-steer` Question 12 (stateless query vs retained query scene vs full world) is **withdrawn for Medieval**; it is not an architectural approval for either a separate scene product or a shared query package. Future real consumers can independently justify those capabilities based on concrete workload and owner authority.
- **Migration and evidence:** [Medieval #76](https://github.com/moritzbrantner/medieval/issues/76) owns the code/dependency removal, exact threshold/boundary tests, `Cargo.lock` cleanup and normal native/WASM tactical acceptance. The existing dependency remains until that issue actually lands; do not mark it removed because this documentation merges. Reconcile [the consumer contract](world-api-contract.md#medieval-legacy-geometry-only-caller-with-approved-removal) and the [Physics Engine roadmap #191](https://github.com/moritzbrantner/physics-engine/issues/191), without creating a duplicate physics migration issue.
- **Reconsider when:** Medieval—or another named consumer—has a concrete requirement for **authoritative physical motion/response** beyond tactical geometry and can prove need, semantics and acceptance. Keep that as a separate feature decision rather than pre-emptive infrastructure.
